# 日志监控与规则提醒设计

## 目标

为 FxTools 增加常驻“日志监控”模块。用户可以选择一个日志文件，配置多条匹配规则，并在新增日志命中规则时收到置顶弹窗提醒。模块在主窗口隐藏到系统托盘后继续运行，应用重启后恢复已保存的配置和启用状态。

初始默认日志路径为当前用户桌面下的 `cc-switch.log`，即在当前需求环境中解析为 `C:\Users\Admin\Desktop\cc-switch.log`。默认启用两条完整 token 规则：`429` 和 `503`。

## 非目标

- 不扫描监听开始前的历史日志。
- 不同时监听多个文件。
- 不提供日志全文查看器或日志归档能力。
- 不将文件不存在、权限不足等读取问题作为业务规则命中弹窗。
- 首版不开放轮询周期、字符集和冷却时间配置；这些值在服务边界内集中定义，便于后续扩展。

## 用户界面

在“系统与开发”导航组新增“日志监控”模块。页面包含：

1. 日志文件区域：路径输入框、文件选择按钮、保存配置按钮、启动/停止按钮和当前监听状态。
2. 规则编辑区域：规则名称、匹配内容、匹配方式、区分大小写和启用状态；支持新增、更新、删除规则。
3. 规则表格：显示每条规则的名称、表达式、方式、大小写和启用状态。
4. 最近命中表格：显示时间、规则、匹配内容摘要和原始日志行，最多保留最近 200 条。

启动前校验路径和全部启用规则。路径可以暂时不存在，此时进入“等待文件”状态；空路径、目录路径、空规则表达式、非法正则和完全重复规则会阻止保存或启动，并在页面给出明确错误。

## 配置模型

配置写入 FxTools 用户数据目录中的 `log-monitor.json`，使用现有原子文件写入工具。配置包含：

```json
{
  "enabled": true,
  "logFile": "C:\\Users\\Admin\\Desktop\\cc-switch.log",
  "rules": [
    {
      "id": "stable-rule-id",
      "name": "HTTP 429",
      "expression": "429",
      "mode": "WHOLE_TOKEN",
      "caseSensitive": true,
      "enabled": true
    }
  ]
}
```

规则 ID 在创建时生成并持久化，作为命中聚合和冷却的稳定键。规则名称用于界面与弹窗展示。配置读取失败时保留损坏文件、不覆盖用户数据，回退到默认配置并在系统日志和页面状态中说明原因。

## 匹配规则

`LogMonitorRule` 描述一条规则，`LogMatchMode` 描述匹配策略。首版支持：

- `CONTAINS`：按普通文本执行包含匹配，支持任意多字符表达式。
- `WHOLE_TOKEN`：只在表达式前后不是 Unicode 字母、数字或下划线时命中。默认状态码规则使用该方式，因此 `429` 能命中 `status=429`，但不会命中 `14290`。
- `REGEX`：编译为 Java 正则并使用 `find()` 匹配；关闭大小写敏感时启用 Unicode 不区分大小写选项。

`LogMonitorMatcher` 在规则保存和监听启动前完成编译与校验。每个新增日志行依次应用所有启用规则；同一规则在同一行中即使出现多次，也只生成一个命中事件。不同规则可以同时命中同一行。完全相同的“匹配方式、表达式、大小写选项”不允许重复，以免产生重复提醒。

命中事件包含规则 ID、规则名称、表达式、文件路径、原始日志行和命中时间。匹配器不依赖 JavaFX、调度器或持久化代码。

## 增量读取

采用单线程守护调度器，每 500 毫秒执行一次增量读取。`LogFileTailer` 负责：

- 首次看到目标文件时记录当前文件末尾，不返回历史内容。
- 只返回上次读取位置之后新增的完整日志行。
- 缓存跨轮询的未完成行和 UTF-8 部分字节。
- 兼容 `LF` 与 `CRLF` 换行并移除 ANSI 控制序列。
- 单行最多保留 32 KiB，超出部分截断并增加说明。
- 通过文件标识和大小识别替换、轮转与截断；运行期间产生的新文件内容从开头继续读取。
- 文件暂时不存在时进入等待状态；重新出现时自动恢复。

`LogMonitorService` 管理 tailer、匹配器与调度生命周期，向监听者发布状态变化、命中事件和读取错误。相同读取错误只在状态变化时记录一次，避免每 500 毫秒刷日志。开始、停止和清理操作幂等，退出应用时关闭调度器。

## 弹窗与去重

`LogMonitorAlertService` 在 JavaFX 线程维护全局唯一的非阻塞提醒弹窗。弹窗展示规则名称、累计次数、首次/最近命中时间以及有限长度的最近日志内容。

- 弹窗打开期间的新命中直接并入当前弹窗并刷新内容，不创建第二个窗口。
- 用户关闭弹窗后，对已展示规则分别开始 60 秒冷却。
- 冷却期内的新命中继续按规则累计，不重复弹出。
- 冷却到期后，如果存在累计命中，自动显示一次合并汇总；没有新命中则不弹窗。
- 多条规则同时到期或同时命中时合并到同一个弹窗中。
- 提醒音复用现有“提醒时播放声音”设置，每次实际展示弹窗最多播放一次。

当主窗口隐藏或最小化时，弹窗沿用备忘提醒的窗口恢复和置顶逻辑，确保用户可见。应用退出时关闭弹窗并取消待触发的冷却任务。

## 架构与数据流

新增或调整的职责边界如下：

- `LogFileTailer`：通用增量文件读取，不了解匹配规则。
- `LogMonitorMatcher`：规则校验、编译和逐行匹配。
- `LogMonitorStore`：配置 JSON 的读取、验证和原子写入。
- `LogMonitorService`：500 毫秒调度、状态机和命中事件发布。
- `LogMonitorAlertService`：命中聚合、冷却和 JavaFX 弹窗生命周期。
- `LogMonitorController`：表单、规则表格、命中表格和服务编排。
- `MainController`：注册模块、应用启动时加载模块、注入主舞台和声音设置、退出时清理。

数据流：

```text
日志文件新增字节
  -> LogFileTailer 返回完整新增行
  -> LogMonitorMatcher 产生规则命中事件
  -> LogMonitorService 发布事件
  -> LogMonitorController 更新最近命中
  -> LogMonitorAlertService 聚合并提醒
```

后台线程不直接访问 JavaFX 控件。控制器使用 `Platform.runLater` 将状态和命中批量传递到 JavaFX 线程。

## 状态与错误处理

监听状态至少包括：`STOPPED`、`WAITING_FOR_FILE`、`RUNNING` 和 `ERROR`。

- 用户手动停止后持久化 `enabled=false`，应用下次启动不自动监听。
- 用户启动成功后持久化 `enabled=true`；应用重启时自动恢复监听。
- 文件不存在为可恢复等待状态，不弹错误框。
- 路径变为目录、权限不足或读取失败时进入错误状态，并继续有限频率重试；恢复后回到运行状态。
- 保存配置失败时保留当前运行配置，不用未持久化配置替换已运行服务。
- 编辑路径或规则时先停止当前监听，保存成功后再按用户操作重新启动，避免运行配置与界面配置不一致。
- 服务和弹窗回调在应用关闭后忽略迟到事件。

## 测试策略

实现采用测试驱动开发，按以下行为逐步完成：

1. `LogMonitorMatcherTest`：三种匹配方式、多字符、大小写、Unicode token 边界、非法正则、重复规则和同一行单规则只命中一次。
2. `LogFileTailerTest`：忽略历史内容、增量行、UTF-8 分段、CRLF、ANSI、超长行、截断、替换、暂缺后首次出现。
3. `LogMonitorStoreTest`：默认配置、往返保存、严格字段校验、非法规则和损坏配置回退边界。
4. `LogMonitorServiceTest`：启停幂等、等待文件、状态恢复、只发布新增命中、读取错误限流和清理后不再回调。
5. `LogAlertAccumulatorTest`：弹窗打开期间聚合、按规则冷却、冷却到期汇总、不同规则合并和有界日志摘要。将时间作为依赖注入，避免真实等待 60 秒。
6. FXML 回归测试：主界面导航、Tab 与新页面 FXML 可加载，所有 `fx:id` 和处理方法存在。
7. 运行完整 Maven 测试套件，并额外启动 JavaFX 应用进行手工验证：监听 `cc-switch.log`，追加普通行不提醒，追加 `429`、`503` 和多字符/正则示例时正确聚合提醒。

## 验收标准

- 可在界面选择并保存 `C:\Users\Admin\Desktop\cc-switch.log`。
- 默认 `429`、`503` 完整 token 规则只匹配启动监听后的新增日志。
- 可创建普通包含、完整 token 和正则三类多字符规则。
- 主窗口隐藏到托盘后仍持续监听并显示置顶提醒。
- 连续命中不会产生弹窗风暴，冷却期间的命中不会丢失汇总。
- 文件暂缺、截断、轮转和重新创建后可自动恢复。
- 应用重启可恢复配置和启用状态，退出后无残留监听线程或弹窗。
- 新增测试与现有完整测试套件全部通过。
